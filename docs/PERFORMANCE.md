# 四玩家操作响应排查（2026-11-03）

用户报告点击投骰和提交答案后等待较久。当前云环境访问线上Render域名被网络策略403拒绝，因此无法测量真实公网延迟、实例CPU或部署地域，不能把本地结果当作线上延迟，也不能断言Render服务器是唯一原因。

## 已确认并修正的程序问题

- SQLite保存原来使用同步写文件、fsync和rename，且每次操作额外导出整库作为备份；改为异步文件I/O，并复用上一次已成功落盘的快照进行错误恢复。成功确认仍在fsync与原子替换完成之后。
- 一个SQLite文件的多房间写入统一排队，防止异步写盘互相覆盖。回归测试包含并发写两个房间、故意制造写盘失败、恢复后重启读回。
- 操作提交者在持久化完成后立即收到自己的新状态；其他连接在40ms窗口合并更新。重复版本不重复发送，在线人数变化仍会通知所有连接。
- 公共统计每轮广播计算一次；个人答案只合并到各自连接，主持人私密视图单独生成；身份缓存仍检查当前凭证和移除状态。
- 投骰、代表申请和答题按钮立即显示进行中状态，并防止同一客户端重复发起尚未完成的操作。

## 本地对照

相同基准：4名玩家＋主持人＋大屏，共6条真实Socket.IO WebSocket连接，40次真实答题提交。临时复制同一份历史测试数据库；运行后数据库均约856KiB。测试不会修改原数据库。

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 提交确认p50 | 9.61ms | 7.24ms |
| 提交确认p95（小样本近似） | 26.70ms | 12.57ms |
| 最大确认耗时 | 38.58ms | 18.17ms |
| 最大事件循环延迟 | 34.01ms | 9.99ms |
| 6个连接合计收到的状态帧 | 240 | 75 |

以上为首次本地一次对照。后续一次非交替复测曾出现约94ms的p95，说明本机负载与调度会影响结果。因此停止其他测试进程，将已发布的旧版与当前版本各跑5次、交替执行，得到：

| 5次交替测量 | 旧版 | 优化版 |
|---|---:|---:|
| 各次p95的中位数 | 16.37ms | 11.04ms |
| 各次p95范围 | 14.14–41.58ms | 10.56–16.90ms |
| 总状态帧数中位数 | 240 | 70 |

这些是本机局部比较，不是生产SLA或1500人压测结果。公网往返、免费实例CPU配额和冷启动均未包含，也不能据此确认用户线上秒级卡顿的主因。使用以下命令可在目标机器复测：

```bash
npm run benchmark:four
# 可指定要临时复制的数据库；不设置时使用当前data/game.sqlite。
BENCHMARK_SEED_FILE=/path/to/game.sqlite npm run benchmark:four
```

浏览器回归在额外600ms的服务处理等待下，实际检查“正在投骰／正在提交”即时出现、按钮禁用，以及后续三端同步、投票修改、坐标、排名与名单下载。

```bash
NODE_ENV=production node tests/slow-server.mjs
E2E_BASE_URL=http://127.0.0.1:3003 E2E_DELAY_ENDPOINT=/_test/delay python tests/browser.py
```

延迟模拟接口只存在于这个绑定127.0.0.1的测试进程，生产服务没有该接口。

## 保留的边界

投骰保留1秒滚动动画，逐格移动至少500ms、每格240ms；这部分是可见的游戏节奏，并非提交确认耗时。公布答案后的奖励展示也保留原有时序。

当前Render免费模式仍为临时存储；部署或服务重启后旧房间可能需要重新创建。持续的秒级提交等待还需要线上网络和实例监控来确认。1500人目标仍需专项改造与压测，本次不作容量承诺。

回归结果：24项通过，1项未配置专用PostgreSQL而明确跳过；类型检查、ESLint、生产构建与慢响应浏览器流程通过。
